# Saffy Decision Log

This document records product decisions made during the development of Saffy.

It preserves both current and historical decisions so that the reasoning behind
Saffy's development is not lost.

Where a decision has been superseded, resolved or duplicated, this is recorded
in its status rather than deleting the original decision.

The current `PRODUCT_SPEC.md` defines Saffy's intended product behaviour.
Where an older decision conflicts with the current Product Specification, the
current Product Specification takes precedence unless a newer explicit decision
says otherwise.

| 008 | Lessons may include prompts the learner has previously answered correctly. A correct answer does not remove a prompt from future lessons. Successful recall is evidence of learning, not evidence that a memory no longer needs retrieval practice. | 009 | Correct once ≠ mastered | Mastery should reflect repeated successful recall rather than a single correct answer. | Confirmed |

| 019 | AI will not determine the underlying mastery score in the MVP | Mastery should initially be based on observable retrieval performance and an evidence-based memory model; AI can later enhance personalisation without making the core score opaque. | Confirmed |
| 020 | AI should be used selectively rather than being the foundation of Saffy's MVP | This keeps costs and complexity down while ensuring the core product remains Saffy's learning system rather than a wrapper around an LLM. | Confirmed |
| 021 | Saffy's initial V1 learning loop is defined | Saffy tests all knowledge items, records every attempt, identifies weak items, supports memory cues. Repeated successful recall increases mastery; repeated mistakes slow/reduce it; performance over time carries more weight than repeated recall in quick succession. | Confirmed |
| 022 | Build Saffy's core learning loop before Login/Sign Up | Authentication doesn't help validate whether Saffy's learning experience works and would introduce Supabase/database complexity too early. Development will prioritise Home → Create Topic → Add Content → Topic Summary → Recall → Feedback → Results → Test Again. Early data can be stored locally on the device; authentication and cloud persistence will be introduced once the core loop works. | Confirmed |
| 023 | Support multiple recall/testing modes in future versions | The MVP will continue to use typed recall with deterministic answer checking. In future, Saffy should support different testing formats depending on the type of knowledge, including multiple choice, self-assessed recall, AI-evaluated free-text responses, and AI-evaluated spoken/voice recall. Exact typed recall works well for vocabulary, terminology, dates and short factual answers, but is less suitable for recalling larger or conceptual bodies of knowledge, such as medical content. Different knowledge types require different ways of demonstrating recall. | Post-MVP / Roadmap |

| 025 | Support multiple recall/testing modes in future versions | The MVP will continue to use typed recall with deterministic answer checking. Future versions may support multiple choice, self-assessed recall, AI-evaluated free-text responses and AI-evaluated spoken/voice recall. Exact typed recall works well for vocabulary and short factual answers but is less suitable for large conceptual answers. | Post-MVP / Roadmap — Duplicate of 023 |
| 026 | Minimum of 10 prompts required to create a topic | Ten prompts gives Saffy enough content to create a meaningful recall session while remaining manageable for initial topic creation. | MVP |
| 027 | Allow alternative accepted answers | Strict exact matching was too restrictive during real-world testing. Users can optionally define alternative valid answers using an Also accept field. This allows synonyms or genuinely equivalent answers without requiring AI semantic marking. | MVP |
| 028 | Normalise trivial English answer variations automatically | Saffy should not penalise irrelevant formatting differences. Answer checking ignores capitalisation, leading/trailing whitespace, repeated spaces and leading English articles (a, an, the). French articles are not removed because grammatical gender may be part of what is being learned. | MVP |
| 029 | Give immediate answer feedback during lessons | Users should know immediately whether retrieval was successful. Correct answers show ✓ Correct; incorrect/skipped answers show ✕ Incorrect and the correct answer before advancing. | MVP |
| 030 | Use a single Edit mode on Lesson Preview | Individual Edit buttons created visual clutter. A single Edit button turns the entire prompt list editable, allowing users to amend any question, answer or accepted answer before saving changes. | MVP |
| 031 | Results sections should be collapsible | Lessons may eventually contain dozens or hundreds of prompts. Your Answers, Review and the stronger-memory pile should therefore start collapsed so users are not forced through extremely long result lists. | MVP |
| 032 | Persist learning state per topic | Saffy must remember previous performance after a user exits a lesson. Current MVP persistence stores the latest lesson results and pile assignments locally using AsyncStorage. | MVP / Temporary architecture |
| 033 | Rename Recall pile to Banked | “Review” and “Recall” are too similar and technical. Banked fits the Memory Bank metaphor and gives Saffy more distinctive consumer-facing language. Banked means currently remembered, not permanently mastered. | MVP terminology — Superseded by 038–041. Banked is no longer simply the renamed Recall pile. |
| 034 | Use Depositing as progress language, not a separate pile | Prompts remain in Review while their memory strengthens. “Depositing” can describe progress towards being Banked, reinforcing the Memory Bank metaphor without introducing another category. | MVP terminology / UX — Superseded by 038–041. Depositing became an actual memory state, rather than merely progress language. |
| 035 | A Banked prompt that is forgotten returns to Review | Banked should represent knowledge that the learner currently appears able to retrieve. If a Banked prompt is answered incorrectly or skipped, Saffy should immediately treat it as needing attention again. | MVP learning logic — Superseded by 038–042. The old Review state no longer exists; a forgotten Banked memory now moves to Depositing. |
| 036 | Do not hard-code a four-correct-answer mastery rule without evidence | The previously discussed four-success progression was an arbitrary MVP heuristic and is not how Anki/FSRS works. Saffy should use evidence-based memory scheduling rather than treating a fixed number of successes as proof of retention. | Supersedes earlier concept |
| 037 | Investigate FSRS as the MVP memory scheduler | FSRS models difficulty, stability and retrievability and increases review intervals as memory strengthens. This aligns closely with Saffy’s mission of identifying what a learner is likely to forget and bringing it back at the right time. We will define the Saffy↔FSRS behaviour before implementing it rather than rushing the architecture. | Under consideration for MVP — Resolved by 057–059. FSRS moved from investigation to confirmed MVP architecture. |
| 038 | Replace the two-state Review/Banked concept with three memory stages | A correct answer on the first lesson is not enough evidence that a memory is genuinely established. Saffy needs an intermediate state while it gathers evidence of retention over time. | MVP |
| 039 | User-facing memory states: Seeded → Depositing → Banked | Seeded represents knowledge that has entered the learning cycle but is not yet reliably recalled. Depositing represents knowledge successfully recalled but still being tested over time. Banked replaces the previous idea of “Mastered” and represents knowledge Saffy has strong evidence is durably retained. | MVP terminology |
| 040 | Banked replaces Mastered, not Recall | We initially considered Banked as a replacement for the Recall pile. Further discussion established that one successful recall should not imply something is Banked. Banked should be an earned long-term state. | Supersedes earlier terminology decision |
| 041 | A first correct answer enters Depositing, not Banked | Someone scoring 40/40 in their first lesson has demonstrated immediate retrieval, but not long-term retention. Their prompts should begin the process of being tested over time rather than immediately being considered Banked. | MVP learning logic |
| 042 | Forgotten Banked memories can move backwards | Banked does not mean permanently learned. If later retrieval demonstrates that the learner has forgotten something, Saffy should respond to that evidence and strengthen the memory again. Exact FSRS transition behaviour is still to be defined. | MVP learning logic |
| 043 | Saffy should recommend what to learn rather than requiring users to manage piles themselves | FSRS can identify which memories are due. The primary experience should therefore be Saffy saying something like “12 memories are ready to strengthen”, rather than making the learner decide which pile they ought to practise. | MVP direction |
| 044 | Users retain manual control over their learning | Alongside Saffy's recommended lesson, users should still be able to enter a topic, inspect memory states, practise a particular group or start a Full Lesson whenever they want. | MVP |
| 045 | Recommended lessons may eventually span multiple topics | If a learner has due memories across several topics, Saffy should be capable of assembling one useful session rather than forcing the learner to enter every topic separately. This becomes increasingly important as the user's Library grows. | MVP investigation / roadmap — Superseded by 063. Recommended lessons will not span multiple topics. |
| 046 | Home and Library should have different purposes | Home = Saffy leads. Library = User leads. Home should greet the learner, summarise recent learning, surface useful observations and recommend what to practise. Library should contain topics, creation/editing tools and manual learning controls. | MVP UX direction |
| 047 | Home should demonstrate that Saffy is observing the learner | Home should surface recent activity such as lessons completed, recalls attempted, accuracy, improvements, difficult areas and memory-state changes. This makes Saffy feel attentive rather than functioning as a static flashcard library. | MVP UX direction |
| 048 | First-use Home should differ from returning-user Home | A new learner has no learning data, so an empty statistics dashboard would be poor onboarding. First use should introduce Saffy, explain the basic concept and encourage creation of the first topic. An optional short video/animation tutorial should be explored. | MVP UX direction |
| 049 | Saffy's personality is core to the MVP, even though Saffy is not yet positioned as a full AI tutor | The intended product is a learning companion, not simply a spaced-repetition utility. Saffy should therefore feel like a consistent character early in the product's life. AI does not need to be integrated immediately, but personality should be part of the MVP design. | MVP |
| 050 | Separate Saffy's memory intelligence from her conversational intelligence | FSRS/deterministic systems should determine what is true about the learner's memory and what is due. AI can eventually interpret and communicate those facts in Saffy's voice. This reduces hallucination risk and keeps the learning engine evidence-based. | MVP architecture direction |
| 051 | AI should be used selectively where it materially improves Saffy | Saffy does not need an LLM for deterministic tasks such as exact answer matching or scheduling. Strong MVP candidates for AI include Saffy's companion personality and generating high-quality multiple-choice distractors. Longer-form semantic answer evaluation remains an important future capability. | MVP AI strategy |
| 052 | Multiple-choice distractors can be generated from existing material, but AI is preferred for high-quality options | Random answers from the same topic can create basic MCQs without AI, but may produce obviously irrelevant options. AI can create plausible-but-incorrect distractors grounded in the learner's material, producing a substantially better test of understanding. | MVP investigation |
| 053 | The user's learning material remains the source of truth for AI-generated testing | When AI creates multiple-choice questions/distractors, it should generate the testing format around the user's supplied material rather than silently changing what Saffy considers the correct answer. | MVP AI principle |
| 054 | Saffy's personality will be deliberately designed before AI personality is implemented | Rather than prompting an LLM to be generically “friendly”, we will define who Saffy is: her warmth, intelligence, humour, encouragement style, language, reactions to success/failure, boundaries and characteristic behaviours. | Next product-design task |
| 055 | Cram / Exam Mode will not be included in the initial MVP | Saffy's MVP will optimise for durable long-term learning using appropriately timed retrieval. A future Cram/Exam Mode could allow users to specify a deadline and have Saffy optimise practice for near-term retrievability instead. This is a valuable use case, but introduces a different scheduling objective and should not complicate validation of Saffy's core memory model. | Post-MVP / Roadmap |
| 056 | Future learning goals may be set at topic level | Different topics may have different objectives: e.g. French for long-term retention versus physiology for an exam next week. Future versions should explore allowing a learning goal and optional deadline to be attached to individual topics rather than assuming one account-wide objective. | Post-MVP / Roadmap |
| 057 | FSRS will own Saffy's memory scheduling. Each memory will have its own FSRS state and due date, which Saffy uses to determine when it should next be tested. | Avoids arbitrary scheduling rules. FSRS decides when; Saffy decides the experience. | MVP |
| 058 | For MVP, observed recall will initially map to FSRS as: Correct → Good; Incorrect/Skipped → Again. Hard and Easy will not initially be used. | Saffy observes retrieval performance, so users shouldn't need to self-rate every answer. This mapping will be validated during implementation. | MVP |
| 059 | Saffy will use the maintained ts-fsrs implementation of FSRS rather than building the algorithm itself. | Saffy is built in TypeScript and there is no benefit to recreating an established scheduling algorithm. | MVP |
| 060 | Recommended lessons will be generated from memories that FSRS determines are due. | Saffy can tell learners what needs attention without requiring them to understand or manage spaced repetition themselves. | MVP |
| 061 | Saffy will use FSRS with short-term learning/relearning disabled for the MVP. Memories will not automatically resurface minutes after a lesson. FSRS will instead schedule future reviews based on recall performance. | Saffy is designed around meaningful spaced retrieval rather than immediate drilling. Incorrect memories should return sooner than correctly recalled memories, but not be automatically repeated within the same session or minutes afterwards. | MVP |
| 062 | Recommended lessons will use a configurable lesson size rather than automatically testing every due memory at once. Saffy will recommend a sensible default size, initially around 10 memories, while allowing the learner to choose 5, 10, 15, 20, or All due before starting. | Large topics may contain dozens or hundreds of memories, and testing every due memory in one session could make lessons feel overwhelming. This keeps Saffy in the lead while giving learners control over session length. | MVP |
| 063 | Lessons must contain prompts from one topic only. Saffy should not mix memories from different topics within the same lesson, even where multiple topics have memories due at the same time. | Avoids unnecessary context switching and potentially confusing learning experiences, such as mixing Italian and Arabic vocabulary within one lesson. Recommended learning should still be driven by due memories, but presented within topic boundaries. | MVP |
| 064 | Moving backwards between memory states does not erase a memory's previous learning history. | Seeded, Depositing and Banked represent Saffy's current interpretation of the learner's memory evidence, not resets of the underlying learning record. If a memory moves backwards, Saffy should retain its previous attempts and FSRS history so future scheduling continues to reflect the learner's actual history with that memory. | MVP |
| 065 | The Results screen will show the lesson score, a breakdown of correct/incorrect/skipped answers, the current memory state of prompts tested, and any memory-state changes caused by the lesson. Results represent the lesson just completed and refresh after each lesson rather than acting as a cumulative results dashboard. | A lesson score shows immediate performance, while Seeded/Depositing/Banked shows how that performance contributes to longer-term learning. Keeping these concepts separate prevents a correct answer from being mistaken for durable retention and helps learners see how Saffy's understanding of their memory develops over time. | MVP |
